Deploy a **BurnMint** token pool on Canton, register it on the Token Admin Registry (TAR), and enable a cross-chain lane. Use the [`ccip-starter-kit-canton`](https://github.com/smartcontractkit/ccip-starter-kit-canton) for pool deployment and TAR registration, or submit Ledger API commands directly.

This guide assumes you already have a token instrument live on Canton — for example a Registry instrument from Digital Asset's [Registry utility](https://docs.digitalasset.com/registry/overview), or any instrument supporting CIP-56 with the `BurnMintFactory` interface.

**Scope:** On-ledger pool connection — deploy, TAR registration (including the `BurnMintFactory` setup for custom tokens), and lane enablement. Does not cover end-to-end transfer tests.

<Aside type="note" title="Testnet only">

Starter kit `cct:*` scripts target **Canton testnet** only.

</Aside>

## Prerequisites

- **Instrument (token managed on Canton Ledger)** with known `InstrumentId = { admin, id }`. The admin party must be the same party that will own the token pool.
- **Burn/mint authority** — `instrumentId.admin == poolOwner` (enforced by the BurnMint template and by the starter kit).
- **DARs uploaded and vetted on your participant** — the pool DAR, plus the `ccip-runtime-v2` and CommitteeVerifier DARs required for sending and executing transfers on the lane (not for deploying or owning the pool itself). See [Prerequisites (all CCT guides)](/ccip/canton/tutorials/cross-chain-tokens#prerequisites-all-cct-guides).
- **CCIP contract references** from Chainlink ops: CCIP owner party, Token Admin Registry, RMNRemote, FeeQuoter.
- **Starter kit setup** (if using `cct:*` scripts) — complete [Canton as Source prerequisites](/ccip/canton/tutorials/source/prerequisites) and the [CCT overview](/ccip/canton/tutorials/cross-chain-tokens#starter-kit-cct-scripts).

<Aside type="caution" title="Pool owner trust">

CCIP fully trusts the pool owner party. Whoever owns the pool controls remote-chain configuration, rate limits, fees, and token handling. We strongly recommend pool owner and instrument admin be the same party, decentralized across multiple nodes.

</Aside>

| 3    | Enable lane                | `cct:enable-lane`      | Rate limiters + `ApplyChainUpdates` |

## Step 2 — Register on the Token Admin Registry

TAR maps each instrument to a single token pool. Registration: **propose → accept → set pool**.

  <Fragment slot="tab.1">Starter kit</Fragment>
  <Fragment slot="tab.2">Manual</Fragment>
  <Fragment slot="panel.1">

```bash filename="Terminal"
npm run cct:set-token -- \
  --instrument 'yourParty::1220…::token-id' \
  --poolInstanceId acme-eur-bm-pool
```

**Flags:**

| Flag               | Required | Description                                                                     |
| :----------------- | :------- | :------------------------------------------------------------------------------ |
| `--instrument`     | Yes      | Same instrument ID used in Step 1                                               |
| `--poolInstanceId` | Yes      | `instanceId` from Step 1                                                        |
| `--poolOwner`      | No       | Party that owns the pool contract (defaults to `party` in `canton-config.json`) |
| `--poolAdmin`      | No       | TAR admin party (defaults to `poolOwner`)                                       |
| `--proposeCaller`  | No       | Party that calls `ProposeAdministrator` (defaults to instrument admin)          |
| `--tokenConfigCid` | No       | Resume at `AcceptAdminRole` if `ProposeAdministrator` already succeeded         |
| `--skipAccept`     | No       | Resume at `SetPool` only (skip propose and accept)                              |

The script fetches TAR disclosures from Global EDS, then submits all three TAR choices in sequence.

### TAR choices

All three choices take a `context` argument (`Splice.Api.Token.MetadataV1.ChoiceContext`) — pass an empty context (`{"values": {}}`) unless your token's tooling supplies one.

1. **`ProposeAdministrator`** — CCIP owner or instrument admin. Pass `instrumentId`, `newAdmin`, `context`, `caller`. For new instruments, leave `tokenConfigCid` as `None`. Returns `TokenConfig` CID for next steps.
2. **`AcceptAdminRole`** — Proposed admin exercises with `tokenConfigCid`, `instrumentId`, `context`, `caller`.
3. **`SetPool`** — Admin links instrument to pool via `PoolRegistration` (`poolOwner`, `poolInstanceId` from Step 1), plus `context` and `caller`.

Admin role can be transferred with `TransferAdminRole` → `AcceptAdminRole`.

  </Fragment>
</Tabs>

### Configure the BurnMintFactory

BurnMint pools do not burn or mint instrument supply themselves — they call a **`BurnMintFactory`** (`Splice.Api.Token.BurnMintV1.BurnMintFactory`). The factory contract implements the actual burn (send) and mint (execute) operations against your token, and its contract ID is supplied by the user in the choice context at transfer time.

- **Registry instruments** (created via Digital Asset's [Registry utility](https://docs.digitalasset.com/registry/overview)) already have a factory — the registry resolves it automatically. No action needed.
- **Custom tokens** (any instrument not created via the Registry utility) must deploy their own `BurnMintFactory` contract and serve it from their EDS — see [Serve the factory from your EDS](#serve-the-factory-from-your-eds). The reference implementation is [`LinkRegistry`](https://github.com/smartcontractkit/chainlink-canton/blob/main/contracts/link/daml/Link/Token.daml) (`#link:Link.Token:LinkRegistry`) — a custom-token factory that implements both `TransferFactory` and `BurnMintFactory` for the LINK instrument on Canton.

### Pin the factory on the TAR (optional, advanced)

By default, the factory's contract ID is **not** pinned on the TAR: the pool calls into whatever `BurnMintFactory` the user supplies in the choice context, using the pool owner's authority. As long as only trusted DARs are vetted on the pool owner's participant — specifically DARs containing a `BurnMintFactory` implementation — this is not a concern.

If the pool owner does not fully trust the participant their party is hosted on, they can hard-code the factory's contract ID on the TAR via the `SetBurnMintFactory` choice. The pool then aborts any transfer where the user-supplied factory does not match the pinned one.

<Aside type="caution" title="Only pin long-lived factories">

Pinning only works if the factory's contract ID will never (or very rarely) change — the same restriction as hard-coding preapprovals in `poolReceiveContext` (see [LockRelease preapprovals](/ccip/canton/tutorials/cross-chain-tokens/lock-release-token-pool#set-pool-receive-preapproval)). If the factory is re-created with a new contract ID, every pinned pool must be updated via `SetBurnMintFactory` before transfers can proceed. Only enable this when you know the factory is long-lived and the trust situation calls for it.

</Aside>

`SetBurnMintFactory` is exercised by the token admin on the TAR (same disclosure flow as the other TAR choices):

| Argument          | Value                                                                  |
| :---------------- | :--------------------------------------------------------------------- |
| `tokenConfigCid`  | Current `TokenConfig` CID (re-read it — it rotates on every TAR write) |
| `instrumentId`    | Your instrument's `InstrumentId`                                       |
| `burnMintFactory` | `Some` + your factory's `ContractId`, or `None` to clear               |
| `context`         | Empty `{"values": {}}` unless your tooling supplies one                |
| `caller`          | The token admin party                                                  |

<Aside type="note" title="Factory contract shape (address mode)">

If you serve the factory in `address` mode (see below), your factory template must expose a top-level `instanceId : Text` create argument (no `@`) — the EDS Active Contract Set indexer keys contracts by `instanceId@signatory`, so a template without it cannot be disclosed. `LinkRegistry` shows the expected shape: `registryAdmin`, `registryInstrumentId`, `instanceId`, `registryMeta`. This requirement is specific to the reference EDS in `address` mode — in `url` mode the factory is resolved from the DA registry backend instead, and if you bring your own EDS, its factory-serving requirements apply.

</Aside>

### Serve the factory from your EDS

Senders and executors cannot see your factory contract — your pool operator's EDS must supply it in the token pool API response. The reference EDS supports two factory modes per pool (`[token_pool_api.token_pools.<address>.factory]`):

| Mode      | Config                                                                                                                                                                  | When to use                                                                                                                                              |
| :-------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `address` | `type = "address"`, `template_id` (`#package-name:Module:Entity`), `party`, `instance_address` (`0x…` hashed form)                                                      | Your factory is visible to the EDS's participant — EDS reads it directly from the Active Contract Set.                                                   |
| `url`     | `type = "url"`, `token_standard_url` — on testnet, the DA token-standard backend: `https://api.utilities.digitalasset-staging.com` (**not** a validator scan-proxy URL) | EDS calls the DA registry backend's `getBurnMintFactory` endpoint at serve time — no ledger visibility into the factory needed on the EDS's participant. |

<Aside type="caution" title="URL mode resolves registry instruments only">

`url` mode calls the DA registry's `getBurnMintFactory` endpoint, which only resolves factories for **Registry utility instruments**. Custom (non-registry) tokens must use `address` mode with their own factory contract.

</Aside>

See the reference configs: [`eds-token-pools.toml`](https://github.com/smartcontractkit/chainlink-canton/blob/main/eds/testdata/eds-token-pools.toml) (URL mode) and the EDS [config tests](https://github.com/smartcontractkit/chainlink-canton/blob/main/eds/config/config_test.go) (address mode).

## Step 3 — Enable a lane

Lane enablement wires your pool to a remote chain: three `RateLimiter` contracts plus an `ApplyChainUpdates` exercise on the pool. Use the starter kit or submit the Ledger API commands directly.

<Tabs client:visible>
  <Fragment slot="tab.1">Starter kit</Fragment>
  <Fragment slot="tab.2">Manual</Fragment>
  <Fragment slot="panel.1">

```bash filename="Terminal"
npm run cct:enable-lane -- \
  --kind burnMint \
  --poolInstanceId acme-eur-bm-pool \
  --remotePool 0x… \
  --remoteToken 0x…
```

`--remotePool` and `--remoteToken` are the token pool and token addresses deployed on the remote chain. EVM addresses are automatically left-padded to the 32-byte form the pool expects.

**Flags:**

| Flag                        | Required | Description                                                                                                                                                                                                                          |
| :-------------------------- | :------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--kind`                    | Yes      | Token pool family deployed in Step 1: `burnMint` or `lockRelease`                                                                                                                                                                    |
| `--poolInstanceId`          | Yes      | Token pool instance ID from Step 1                                                                                                                                                                                                   |
| `--remotePool`              | Yes      | Remote token pool address (`0x`-hex) — the pool this lane trusts on the remote chain                                                                                                                                                 |
| `--remoteToken`             | Yes      | Remote token address (`0x`-hex) — the token this lane bridges on the remote chain                                                                                                                                                    |
| `--poolOwner`               | No       | Party that owns the pool contract (defaults to `party` in `canton-config.json`)                                                                                                                                                      |
| `--remoteChainSelector`     | No       | Destination chain selector (defaults to the configured remote chain — Sepolia in the starter kit)                                                                                                                                    |
| `--ccv`                     | No       | CommitteeVerifier raw instance address(es) for both directions (defaults to the CCIP-hosted testnet CCV — the pool itself has no default, so manual `ApplyChainUpdates` must always set `inboundCCVs` and `outboundCCVs` explicitly) |
| `--finality`                | No       | Allowed finality policy for the lane: `finalized` (default) or `blockDepth`                                                                                                                                                          |
| `--blockDepth`              | No       | Block depth (1–65535), required with `--finality blockDepth`                                                                                                                                                                         |
| `--limiterInstanceIdPrefix` | No       | Prefix for the three rate limiter instance IDs (defaults to `<poolInstanceId>-<remoteChainSelector>`)                                                                                                                                |
| `--enableLimiters`          | No       | Deploy the rate limiters enabled (defaults to disabled with zero capacity/rate for testing)                                                                                                                                          |
| `--capacity`                | No       | Rate limiter capacity in the pool's decimal representation (with `--enableLimiters`)                                                                                                                                                 |
| `--rate`                    | No       | Rate limiter refill per second in the pool's decimal representation (with `--enableLimiters`)                                                                                                                                        |

The script deploys the three rate limiters and exercises `ApplyChainUpdates` on the pool in one run.

### 1. Deploy three rate limiters

Each lane requires [`RateLimiter`](https://github.com/smartcontractkit/chainlink-canton/blob/main/contracts/ccip/rate-limiter/daml/CCIP/RateLimiterV2.daml) contracts (for testing, deploy disabled with zero capacity/rate):

- **Inbound (default finality)**
- **Inbound (custom finality)**
- **Outbound**

Created by `poolOwner` with matching `poolInstanceId`, `poolOwner`, and `remoteChainSelector`.

### 2. Apply the chain update

## Step 4 — Go live

### Verification checklist

1. `InstrumentId.admin` equals pool owner.
2. TAR maps your instrument to your pool with your party as admin.
3. Pool exists at `{instanceId}@{poolOwner}` with matching `InstrumentId`.
4. Lane rate limiters are in place.

### Stand up EDS for your pool

Users need [explicit disclosures](/ccip/canton/concepts/explicit-disclosure) for your pool to send and execute transfers. The [reference EDS Docker image](https://github.com/smartcontractkit/chainlink-canton/blob/main/eds/eds.Dockerfile) supports BurnMint out of the box.
