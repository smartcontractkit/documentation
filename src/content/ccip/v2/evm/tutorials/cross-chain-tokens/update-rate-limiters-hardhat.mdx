In this tutorial you will:

1. Review current standard rate limiter configurations for your deployed token pool.
2. Update outbound and inbound standard rate limiter configurations.
3. Verify the updated configurations.
4. Test standard rate limiter enforcement with a cross-chain token transfer.
5. Optionally configure and test rate limits for faster than finality transfers.

## Before You Begin

<AnchoredAccordion title="Set up your development environment" number={1} depth={3}>

1. Install Node.js and npm:
   - Make sure you have `Node.js v22.10.0` or above installed. If not, install **`Node.js v22.10.0`** using their [documentation](https://nodejs.org/en/download/).
   - `npm` is bundled with Node.js. If you can’t run `npm`, reinstall/update Node.js from the official installer.

2. Install/Update [Chainlink CCIP-CLI](https://docs.chain.link/ccip/tools/cli/). You can also find the [GitHub repository here](https://github.com/smartcontractkit/ccip-cli).

```bash filename="Terminal"
npm install -g @chainlink/ccip-cli
```

Verify the installation by running the following command:

```bash filename="Terminal"
ccip-cli --version
```

3. **Clone the repository and navigate to the project directory**:

<GitHubCard
  title="CCIP 2.0 template"
  href="https://github.com/smartcontractkit/docs-cct-hardhat"
  iconName="github-svg-card"
>
  Clone the CCIP 2.0 Hardhat template for a smoother CCT setup.
</GitHubCard>

```bash filename="Terminal"
git clone https://github.com/smartcontractkit/docs-cct-hardhat.git
cd docs-cct-hardhat
```

4. Create a `.env` file by copying the `.env.example` file, and fill in the required values:

```bash filename="Terminal"
cp .env.example .env
```

```bash filename=".env"
# Keystore name (created via `npx hardhat keystore set`)
KEYSTORE_NAME=<your_private_key_name>

# RPC URLs (add the ones you need)
ETHEREUM_SEPOLIA_RPC_URL=your_eth_sepolia_rpc
ARBITRUM_SEPOLIA_RPC_URL=your_arbitrum_sepolia_rpc

# Etherscan API key (required only if you pass --verify to deployment tasks)
ETHERSCAN_API_KEY=your_etherscan_api_key
```

5. To make sure your terminal has access to these variables, run the following command:


6. Build the project:

```bash filename="Terminal"
npm install && npx hardhat compile
```

7. Create an encrypted Hardhat keystore, if you haven't already:

```bash filename="Terminal"
npx hardhat keystore set <your_private_key_name>
```

<AnchoredAccordion title="Update Rate Limiter Configurations" number={2} depth={3}>

Use the `updateRateLimiters` task to update rate limiter configurations for an existing lane in your token pool. The direction to update is inferred automatically from whichever `--outbound*` / `--inbound*` flags you set.

Only the directions you specify are updated; any direction you don't specify is left unchanged. Outbound and inbound are relative to the pool you're configuring:

1. `outbound` is tokens leaving this pool toward the `--destchain` remote chain;
2. `inbound` is tokens arriving from the `--destchain` remote chain into this pool.

<Aside type="note" title="Lane must exist">
  <ol>
    <li>Rate limiters can only be updated for lanes that already exist.</li>
    <li>
      If you haven't configured the lane yet, complete one of the two tutorials first:
      <ul>
        <li>
          <a href="/ccip/evm/tutorials/cross-chain-tokens/register-from-eoa-burn-mint-hardhat">Burn & Mint</a>
        </li>
        <li>
          <a href="/ccip/evm/tutorials/cross-chain-tokens/register-from-eoa-lock-mint-hardhat">Lock & Mint</a>
        </li>
      </ul>
    </li>
    <li>
      Run <code>applyChainUpdates</code> to configure the lane.
    </li>
  </ol>
</Aside>

| <nobr>`--inboundcapacity`</nobr>  | <nobr>To update inbound</nobr>  | <nobr>Token bucket capacity for inbound transfers</nobr>                                                        |
| <nobr>`--inboundrate`</nobr>      | <nobr>To update inbound</nobr>  | <nobr>Token bucket refill rate (tokens/second) for inbound transfers</nobr>                                     |
| <nobr>`--inboundenabled`</nobr>   | <nobr>No</nobr>                 | <nobr>Override `isEnabled` explicitly (`true`/`false`; defaults to `true` when capacity or rate are set)</nobr> |
| <nobr>`--fastfinality`</nobr>     | <nobr>No</nobr>                 | <nobr>Update the faster than finality bucket instead of the standard finality bucket (v2 only)</nobr>           |

<Aside type="note" title="Access control and compatibility">
  <ol>
    <li>
      The pool owner and the designated <code>rateLimitAdmin</code> can update rate limiters.
    </li>
    <li>
      The <code>rateLimitAdmin</code> is configured via <code>setDynamicConfig</code>.
    </li>
    <li>
      This task supports both v1 and v2 token pools: on v2 pools it calls <code>setRateLimitConfig()</code>; on v1 pools
      it falls back to <code>setChainRateLimiterConfig()</code>.
    </li>
    <li>
      The <code>--fastfinality</code> flag is v2-only and is ignored on v1 pools.
    </li>
  </ol>
</Aside>

<Aside type="note" title="Configuration best practices">
  <ol>
    <li>
      Set inbound rate limits a bit higher than outbound limits on the same lane. Many chains finalize blocks in
      batches, so multiple outbound messages may become executable on the destination simultaneously, requiring slightly
      more inbound capacity.
    </li>
    <li>
      The exact additional capacity required depends on the refill rate and the size of the source chain epochs and CCIP
      round time. In most cases, a 5-10% buffer should be sufficient.
    </li>
    <li>
      <code>rate</code> must be less than or equal to <code>capacity</code>, and when disabling rate limiting (
      <code>isEnabled: false</code>), both <code>capacity</code> and <code>rate</code> must be <code>0</code>.
    </li>
  </ol>
</Aside>

<AnchoredAccordion title="Test the Rate Limiter Configurations" number={4} depth={3}>

Initiate a cross-chain transfer to verify that the rate limiter enforces the configured limits.

<Aside type="note" title="Token balance">
  Ensure your EOA has a sufficient balance of the cross-chain token on the source chain. If you need more tokens, use
  the <code>mintTokens</code> task or transfer tokens from another account.
</Aside>

Before testing, export the router and token addresses for the source chain:

```bash filename="Terminal"
export ETHEREUM_SEPOLIA_ROUTER=0x...
export ETHEREUM_SEPOLIA_TOKEN=0x...
```

<Aside type="note" title="Router address">
  You can find the router address for your chain in the [CCIP
  Directory](https://docs.chain.link/ccip/directory/testnet).
</Aside>

> **Note:**
>
> 1. Add `--fee-token LINK` to pay CCIP fees in LINK. If you omit this flag, fees are paid in the native gas token.
> 2. Use `--receiver <address>` for a custom recipient. If omitted on EVM-to-EVM, the receiver defaults to the sender.

#### Test 1: Exceed capacity

Transfer one wei more than the outbound capacity (10 tokens + 1 wei). This should fail because the requested amount exceeds the bucket size.

```bash filename="Terminal"
ccip-cli send \
  --source ethereum-testnet-sepolia \
  --router $ETHEREUM_SEPOLIA_ROUTER \
  --dest ethereum-testnet-sepolia-arbitrum-1 \
  --transfer-tokens $ETHEREUM_SEPOLIA_TOKEN=10.000000000000000001 \
  --wallet hardhat:$KEYSTORE_NAME \
  --rpc "$ETHEREUM_SEPOLIA_RPC_URL" \
  --rpc "$ARBITRUM_SEPOLIA_RPC_URL"
```

Your output should look something like this:

```bash filename="Terminal"
Fee: 130129888907619n = 0.000130129888907619 ETH
✔ Enter password for Hardhat keystore 'PRIVATE_KEY'
error: Failed to call "ccipSend"
Error = execution reverted: TokenMaxCapacityExceeded(uint256 capacity, uint256 requested, address tokenAddress)
Revert.error = TokenMaxCapacityExceeded(uint256,uint256,address)
Revert.capacity = 10000000000000000000n
Revert.requested = 10000000000000000001n
Revert.tokenAddress = 0x9602399103Ff5F87587Ac5A28E1551A0bA0c6C0D
```

The transfer should fail with `TokenMaxCapacityExceeded` because the requested amount is larger than the bucket capacity.

<Aside type="note" title="How does the token bucket work?">
  CCIP rate limiters use a <em>token bucket</em> model. Think of the bucket as a virtual allowance that controls how
  many tokens can flow through the pool in a given window:
  <ol>
    <li>
      The bucket starts full at its configured <strong>capacity</strong>.
    </li>
    <li>
      Each transfer <strong>consumes</strong> its amount from the bucket.
    </li>
    <li>
      The bucket <strong>refills</strong> continuously at the configured <strong>rate</strong> (tokens per second).
    </li>
  </ol>
  In this tutorial, the outbound bucket has a capacity of 10 tokens and refills at 0.1 tokens/sec. Transferring all 10
  tokens in one go "drains" the bucket to zero. Any immediate follow-up transfer will fail because the bucket needs 100
  seconds (10 &divide; 0.1) to fully replenish.
</Aside>

#### Test 2: Drain the bucket, then hit the rate

1. **First transfer** (succeeds: drains the outbound bucket):

```bash filename="Terminal"
ccip-cli send \
  --source ethereum-testnet-sepolia \
  --router $ETHEREUM_SEPOLIA_ROUTER \
```

<AnchoredAccordion title="(Optional) Configure Rate Limits for Faster Than Finality Transfers" number={5} depth={3}>

This section applies to [`TokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/TokenPool.sol) v2.0 or later only. CCIP 2.0 token pools maintain two independent rate limiter buckets per lane:

- **Standard finality bucket**: Used for standard finality transfers (`finality=finalized`, which is the default when you omit `--extra finality=...`). This is the bucket you configured in the previous steps.
- **Faster Than Finality bucket**: Used for transfers that request faster than finality with `finality=<N>` (numeric block depth). If this bucket is disabled for a direction, faster than finality transfers for that direction fall back to the standard bucket (enforced on-chain by the token pool).

<Aside type="note" title="Pool type and lockbox scope">
  Rate limiters are configured on token pools, regardless of whether you registered your token with Burn &amp; Mint or
  Lock &amp; Mint. In Lock &amp; Mint, the <code>ERC20LockBox</code> is not rate-limited and is not updated by these
  tasks.
</Aside>

<Aside type="caution" title="Faster Than Finality must be allowed first">
  <ol>
    <li>
      Updating the faster than finality bucket alone does <strong>not</strong> enable faster than finality transfers.
      The pool owner must also configure the pool's <strong>allowed finality config</strong> with{" "}
      <code>setFinalityConfig</code>.
    </li>
    <li>
      Setting the allowed finality config is owner-only. Updating rate limiters can be done by the pool owner or the
      configured <code>rateLimitAdmin</code>.
    </li>
    <li>
      For the full faster than finality setup flow, see the Configure Faster Than Finality section in either
      registration tutorial:
      <ul>
        <li>
          <a href="/ccip/evm/tutorials/cross-chain-tokens/register-from-eoa-burn-mint-hardhat#optional-configure-fast-finality-for-the-token-pool">
            Burn &amp; Mint
          </a>
        </li>
        <li>
          <a href="/ccip/evm/tutorials/cross-chain-tokens/register-from-eoa-lock-mint-hardhat#optional-configure-fast-finality-for-the-token-pool">
            Lock &amp; Mint
          </a>
        </li>
      </ul>
    </li>
  </ol>
</Aside>
