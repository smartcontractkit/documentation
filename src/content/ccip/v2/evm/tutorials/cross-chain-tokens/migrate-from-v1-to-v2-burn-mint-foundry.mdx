This migration guide helps you upgrade a deployed **Burn & Mint** Cross-Chain Token (CCT) setup from **CCIP v1 (1.5.x / 1.6.x)** to **CCIP v2**, while keeping your existing token addresses and minimizing disruption.

This guide uses Foundry scripts inside our [docs-cct-foundry](https://github.com/smartcontractkit/docs-cct-foundry) repository.

<Aside type="note" title="Finality and v2 features are optional">
  <ol>
    <li>
      <strong>Default finality:</strong> Transfers use the chain’s native finality unless you explicitly opt into
      block-depth faster than finality.
    </li>
    <li>
      <strong>Opt-in changes:</strong> Pool-level fees, faster than finality, and hooks only apply if you configure
      them. This guide focuses on a safe pool migration first.
    </li>
  </ol>
</Aside>

In this guide you will:

1. Confirm prerequisites and record your existing CCIP v1 deployment details.
2. Deploy new CCIP v2 `Burn Mint` token pools on each chain.
3. Configure the v2 pools to accept messages from **both** the old v1 pools and the new v2 pools.
4. Cut over CCIP routing by calling [`TokenAdminRegistry`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/tokenAdminRegistry/TokenAdminRegistry.sol).setPool on each chain.
5. Validate transfers end-to-end, then optionally clean up legacy configuration.

## Before You Begin

<AnchoredAccordion title="Set up your development environment" number={1} depth={3}>

1. Install Node.js and npm:
   - Make sure you have `Node.js v22.10.0` or above installed. If not, install **`Node.js v22.10.0`** using their
     [documentation](https://nodejs.org/en/download/).
   - `npm` is bundled with Node.js. If you can’t run `npm`, reinstall/update Node.js from the official installer.

2. Install/Update [Chainlink CCIP-CLI](https://docs.chain.link/ccip/tools/cli/). You can also find the [GitHub repository here](https://github.com/smartcontractkit/ccip-cli).

```bash filename="Terminal"
npm install -g @chainlink/ccip-cli
```

Verify the installation by running the following command:

```bash filename="Terminal"
ccip-cli --version
```

3. **Install Foundry**:
   If you haven't already, follow the instructions in the [Foundry documentation](https://book.getfoundry.sh/getting-started/installation) to install Foundry. \
   Verify the installation by running the following command:

```bash filename="Terminal"
forge --version
```

4. **Clone the repository and navigate to the project directory**:

<GitHubCard
  title="CCIP 2.0 Foundry template"
  href="https://github.com/smartcontractkit/docs-cct-foundry"
  iconName="github-svg-card"
>
  Clone the CCIP 2.0 Foundry template for a smoother CCT setup.
</GitHubCard>

```bash filename="Terminal"
git clone https://github.com/smartcontractkit/docs-cct-foundry.git
cd docs-cct-foundry
```

5. Create an encrypted Foundry keystore, if you haven't already:

```bash filename="Terminal"
cast wallet import your_keystore_name --interactive
```

6. Create a `.env` file by copying the `.env.example` file, and fill in the required values:

```bash filename="Terminal"
cp .env.example .env
```

```bash filename=".env"
# Keystore name (created via `cast wallet import`)
KEYSTORE_NAME=your_keystore_name

# RPC URLs (lane used in this guide)
ETHEREUM_SEPOLIA_RPC_URL=your_eth_sepolia_rpc
ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1_RPC_URL=your_arbitrum_sepolia_rpc

# Etherscan API key (required only if you pass --verify to deployment scripts)
ETHERSCAN_API_KEY=your_etherscan_api_key
```

<GitHubCard
  title="Complete List of Supported Chains"
  href="https://github.com/smartcontractkit/docs-cct-foundry/blob/main/script/HelperConfig.s.sol"
  iconName="github-svg-card"
>
  View the complete list of supported chains in the <code>HelperConfig.s.sol</code> file.
</GitHubCard>

7. To make sure your terminal has access to these variables, run the following command:

```bash filename="Terminal"
source .env
```

8. Install dependencies and build the project:

```bash filename="Terminal"
npm install && forge build
```

</AnchoredAccordion>

<AnchoredAccordion title="What this guide assumes" number={2} depth={3}>
  - **EVM-to-EVM only**: this page is strictly for **Ethereum Sepolia ↔ Arbitrum Sepolia**. - **Burn & Mint pools
  only**: standard
  [`BurnMintTokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/BurnMintTokenPool.sol)
  migrations (no custom pools). - You control the `TokenAdminRegistry` **administrator** role for the token **on both
  chains**. - You can grant the required **mint/burn** permissions to the new v2 pools on each chain. - You can execute
  **pool-owner** actions on both chains (for example, `applyChainUpdates`, `removeRemotePool`). - You are migrating an
  already-live CCIP v1 setup (1.5.x or 1.6.x), not doing a new registration.
</AnchoredAccordion>

## Migration Guide

<Aside type="tip" title="Set these variables once for cleaner copy/paste">

<Aside type="note" title="What to check before continuing">
  <ul>
    <li>
      <strong>administrator</strong> should match the account/multisig you control (this account must execute{" "}
      <code>setPool</code> during cutover).
    </li>
    <li>

<AnchoredAccordion
  title="Step 4 (Recommended): Pause outbound transfers on the v1 pools"
  number={4}
  depth={3}
>

This recommended step throttles new outbound traffic on v1 while you cut over. Use **capacity = 2** and **rate = 1**
as the most restrictive (near-zero) configuration we document for v1 pools while keeping the lane configured.

<Aside type="caution" title="Run Step 2 first if you want the original rate limits">
  Step 4 overwrites the v1 pool’s <strong>outbound</strong> rate limits. If you want to carry your original v1 rate
  limits over to v2, make sure you record them in Step 2 before pausing outbound.
</Aside>

<GitHubCard
  title="UpdateRateLimiters.s.sol"

<AnchoredAccordion title="Step 10: Safety checks and cleanup (after v1 inflight settles)" number={10} depth={3}>

After cutover, keep the v1 remote pool addresses configured on the v2 pools until you are confident there are no more
in-flight v1 messages. There is no cost to waiting longer.

Once you’re ready, remove the **old v1 remote pool addresses** from the v2 pools.

<GitHubCard
  title="RemoveRemotePool.s.sol"
  href="https://github.com/smartcontractkit/docs-cct-foundry/blob/main/script/configure/remote-pools/RemoveRemotePool.s.sol"
  iconName="github-svg-card"
>
  View the remote pool removal script on GitHub.
</GitHubCard>

1. On the **Sepolia v2 pool**, remove the old Arbitrum v1 pool address:

```bash filename="Terminal"
TOKEN_POOL=$ETHEREUM_SEPOLIA_V2_POOL \
  DEST_CHAIN=ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1 \
  REMOTE_POOL_ADDRESS=$ARBITRUM_SEPOLIA_V1_POOL \
  forge script \
  script/configure/remote-pools/RemoveRemotePool.s.sol \
  --rpc-url $ETHEREUM_SEPOLIA_RPC_URL \
  --account $KEYSTORE_NAME \
  --broadcast
```

Your output should look something like this:

```bash filename="Terminal"
⚠️  WARNING: All inflight transactions from this pool will be rejected after removal.

Current Remote Pools: 2
  [0] 0xOldArbitrumV1PoolAddress
  [1] 0xNewArbitrumV2PoolAddress

✅ Remote pool removed successfully!
```

2. On the **Arbitrum v2 pool**, remove the old Sepolia v1 pool address:

```bash filename="Terminal"
TOKEN_POOL=$ARBITRUM_SEPOLIA_V2_POOL \
  DEST_CHAIN=ETHEREUM_SEPOLIA \
  REMOTE_POOL_ADDRESS=$ETHEREUM_SEPOLIA_V1_POOL \
  forge script \
  script/configure/remote-pools/RemoveRemotePool.s.sol \
  --rpc-url $ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1_RPC_URL \
  --account $KEYSTORE_NAME \
  --broadcast
```

<Aside type="caution" title="If you removed too early">
  If a v1-sent message is still in-flight and you removed its source pool address, it can fail validation on the
  destination. You can recover by adding the pool address back with <code>AddRemotePool</code>, then retry cleanup
  later.
</Aside>

<GitHubCard
  title="AddRemotePool.s.sol"
  href="https://github.com/smartcontractkit/docs-cct-foundry/blob/main/script/configure/remote-pools/AddRemotePool.s.sol"
  iconName="github-svg-card"
>
  View the remote pool add script on GitHub (recovery).
</GitHubCard>

Recovery example (re-add the old pool address, then retry cleanup later):

```bash filename="Terminal"
TOKEN_POOL=$ETHEREUM_SEPOLIA_V2_POOL \
  DEST_CHAIN=ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1 \
  REMOTE_POOL_ADDRESS=$ARBITRUM_SEPOLIA_V1_POOL \
  forge script \
  script/configure/remote-pools/AddRemotePool.s.sol \
  --rpc-url $ETHEREUM_SEPOLIA_RPC_URL \
  --account $KEYSTORE_NAME \
  --broadcast
```

<Aside type="note" title="Optional hardening">
  After migration and cleanup, you can also revoke mint/burn roles from the old v1 pools (if your token’s access control
  allows it). This is token-specific and may require calling role revocation functions directly on your token contract.
</Aside>
