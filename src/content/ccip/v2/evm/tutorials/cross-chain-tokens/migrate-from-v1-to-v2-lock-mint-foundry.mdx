This migration guide helps you upgrade a deployed **Lock & Mint** Cross-Chain Token (CCT) setup from **CCIP v1 (1.5.x / 1.6.x)** to **CCIP v2**, while keeping your existing token addresses and minimizing disruption.

This guide uses Foundry scripts inside our [docs-cct-foundry](https://github.com/smartcontractkit/docs-cct-foundry) repository.

<Aside type="note" title="Lock & Mint is asymmetric">
  In a Lock & Mint deployment the two chains are **not** symmetric. The canonical (source) chain runs a **Lock &
  Release** pool backed by an **ERC20 lockbox** that holds the locked liquidity; the destination chain runs a **Burn &
  Mint** pool. Because of this, the migration has an extra step that Burn & Mint does not: you must **move the locked
  liquidity** out of the old v1 pool and into the new v2 lockbox.
</Aside>

<Aside type="note" title="Finality and v2 features are optional">
  <ol>
    <li>
      <strong>Default finality:</strong> Transfers use the chain’s native finality unless you explicitly opt into
      block-depth faster than finality.
    </li>
    <li>
      <strong>Opt-in changes:</strong> Pool-level fees, faster than finality, and hooks only apply if you configure
      them. This guide focuses on a safe pool migration first.
    </li>
  </ol>
</Aside>

In this guide you will:

1. Confirm prerequisites and record your existing CCIP v1 deployment details, including the locked liquidity on the canonical chain.
2. Deploy the new CCIP 2.0pools: an [`ERC20LockBox`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/ERC20LockBox.sol) + [`LockReleaseTokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/LockReleaseTokenPool.sol) on the canonical chain, and a [`BurnMintTokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/BurnMintTokenPool.sol) on the destination chain.
3. Pause the old v1 pools and migrate the locked liquidity from the v1 Lock & Release pool into the new lockbox.
4. Configure the v2 pools to accept messages from **both** the old v1 pools and the new v2 pools.
5. Cut over CCIP routing by calling [`TokenAdminRegistry`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/tokenAdminRegistry/TokenAdminRegistry.sol).setPool on each chain, validate transfers end-to-end, then optionally clean up legacy configuration.

## Before You Begin

<AnchoredAccordion title="Set up your development environment" number={1} depth={3}>

1. Install Node.js and npm:
   - Make sure you have `Node.js v22.10.0` or above installed. If not, install **`Node.js v22.10.0`** using their
     [documentation](https://nodejs.org/en/download/).
   - `npm` is bundled with Node.js. If you can’t run `npm`, reinstall/update Node.js from the official installer.

2. Install/Update [Chainlink CCIP-CLI](https://docs.chain.link/ccip/tools/cli/). You can also find the [GitHub repository here](https://github.com/smartcontractkit/ccip-cli).

```bash filename="Terminal"
npm install -g @chainlink/ccip-cli
```

Verify the installation by running the following command:

```bash filename="Terminal"
ccip-cli --version
```

3. **Install Foundry**:
   If you haven't already, follow the instructions in the [Foundry documentation](https://book.getfoundry.sh/getting-started/installation) to install Foundry. \
   Verify the installation by running the following command:

```bash filename="Terminal"
forge --version
```

4. **Clone the repository and navigate to the project directory**:

<GitHubCard
  title="CCIP 2.0 Foundry template"
  href="https://github.com/smartcontractkit/docs-cct-foundry"
  iconName="github-svg-card"

  Clone the CCIP 2.0 Foundry template for a smoother CCT setup.
</GitHubCard>

```bash filename="Terminal"
git clone https://github.com/smartcontractkit/docs-cct-foundry.git
cd docs-cct-foundry
```

5. Create an encrypted Foundry keystore, if you haven't already:

```bash filename="Terminal"
cast wallet import your_keystore_name --interactive
```

6. Create a `.env` file by copying the `.env.example` file, and fill in the required values:

```bash filename=".env"
# Etherscan API key (required only if you pass --verify to deployment scripts)
ETHERSCAN_API_KEY=your_etherscan_api_key
```

<AnchoredAccordion title="What this guide assumes" number={2} depth={3}>

- **EVM-to-EVM only**: this page is strictly for **Ethereum Sepolia ↔ Arbitrum Sepolia**.
- **Asymmetric Lock & Mint topology**: **Ethereum Sepolia** is the **canonical / Lock & Release** chain (it holds the `ERC20LockBox` and the `LockReleaseTokenPool`); **Arbitrum Sepolia** is the **destination / Burn & Mint** chain (it holds the `BurnMintTokenPool`).
- **Standard pools only**: a single shared lockbox with `LockReleaseTokenPool` (not [`SiloedLockReleaseTokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/SiloedLockReleaseTokenPool.sol)) and a standard `BurnMintTokenPool` (no custom pools).
- You control the `TokenAdminRegistry` **administrator** role for the token **on both chains**.
- You own the **v1 pools on both chains** (needed for `setRebalancer`, `withdrawLiquidity`, `applyChainUpdates`, and `removeRemotePool`).
- You can grant the required **mint/burn** permissions to the new v2 `BurnMintTokenPool` on **Arbitrum Sepolia**.
- You are migrating an already-live CCIP v1 setup (1.5.x or 1.6.x), not doing a new registration.

</AnchoredAccordion>

## Migration Guide

<br />

<Aside type="tip" title="Set these variables once for cleaner copy/paste">
  This guide uses explicit addresses so you don’t need local <code>script/deployments/</code> files. Start by exporting
  your token addresses; we’ll export the v1/v2 pool addresses and the lockbox address as we discover or deploy them.

```bash filename="Terminal"
export ETHEREUM_SEPOLIA_TOKEN=0x...
export ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1_TOKEN=0x...
```

</Aside>

<AnchoredAccordion title="Step 1: Confirm the live CCIP v1 pools (and record v1 addresses)" number={1} depth={3}>

This step answers two questions, on **both chains**:

1. **Which pool is currently live for your token?** (read from `TokenAdminRegistry.getTokenConfig`)
2. **Is that pool a v1.5/v1.6 pool?** (read `typeAndVersion()` from the pool)

Because Lock & Mint is asymmetric, expect a **`LockReleaseTokenPool`** on Ethereum Sepolia and a **`BurnMintTokenPool`** on Arbitrum Sepolia.

<Aside type="note" title="What to check before continuing">
  <ul>
    <li>
      <strong>administrator</strong> should match the account/multisig you control (this account must execute{" "}
      <code>setPool</code> during cutover).
    </li>
    <li>
      <strong>pendingAdministrator</strong> should typically be <code>0x0</code>. If it’s set, resolve it before
      migrating to avoid confusion.
    </li>
    <li>
      <strong>typeAndVersion</strong> should indicate a v1.5.x or v1.6.x <code>LockReleaseTokenPool</code> on Ethereum
      Sepolia and a v1.5.x or v1.6.x <code>BurnMintTokenPool</code> on Arbitrum Sepolia.
    </li>
  </ul>
</Aside>

```bash filename="Terminal"

  $ETHEREUM_SEPOLIA_V1_POOL \
```

  limits over to v2, make sure you record them here first.
</Aside>

<Aside type="caution" title="If the role grant is skipped">
  The deploy script tries to call <code>grantMintAndBurnRoles</code> on your Arbitrum token. If your token predates that
  interface, the script prints a warning instead of <code>✅ Roles granted successfully!</code> and you must grant{" "}
  <strong>mint</strong> and <strong>burn</strong> roles to <code>$ARBITRUM_SEPOLIA_V2_POOL</code> yourself, using

  Until post-migration cleanup, <strong>both</strong> v1 and v2 Burn &amp; Mint pools may hold mint/burn roles on your

  <strong>empty</strong> (no liquidity yet). Your CCIP routing still points to the v1 pools until Step 8.
</Aside>

<AnchoredAccordion
  title="Step 4 (Required): Pause outbound transfers on the v1 pools"
  number={4}
  depth={3}
>

For Lock & Mint this step is **required**, not optional: Step 5 drains the old v1 Lock & Release pool, and pausing prevents new transfers from locking additional tokens (which would be stranded outside the lockbox). Use **capacity = 2** and **rate = 1**: the most restrictive (near-zero) configuration we document that works across all v1 pool versions while keeping the lane configured. Only the **outbound** direction is changed; inbound is left as-is so in-flight messages can still arrive.

<GitHubCard
  title="UpdateRateLimiters.s.sol"
  href="https://github.com/smartcontractkit/docs-cct-foundry/blob/main/script/configure/rate-limiter/UpdateRateLimiters.s.sol"
  iconName="github-svg-card"
>
  View the rate limiter update script on GitHub.
</GitHubCard>

1. Pause outbound on the **Sepolia v1 pool** (lane to Arbitrum Sepolia):

```bash filename="Terminal"
TOKEN_POOL=$ETHEREUM_SEPOLIA_V1_POOL \
  DEST_CHAIN=ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1 \
  OUTBOUND_RATE_LIMIT_CAPACITY=2 \
  OUTBOUND_RATE_LIMIT_RATE=1 \
  forge script \
  script/configure/rate-limiter/UpdateRateLimiters.s.sol \
  --rpc-url $ETHEREUM_SEPOLIA_RPC_URL \
  --account $KEYSTORE_NAME \
  --broadcast
```

2. Pause outbound on the **Arbitrum v1 pool** (lane to Ethereum Sepolia):

```bash filename="Terminal"
TOKEN_POOL=$ARBITRUM_SEPOLIA_V1_POOL \
  DEST_CHAIN=ETHEREUM_SEPOLIA \
  OUTBOUND_RATE_LIMIT_CAPACITY=2 \
  OUTBOUND_RATE_LIMIT_RATE=1 \
  forge script \
  script/configure/rate-limiter/UpdateRateLimiters.s.sol \
  --rpc-url $ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1_RPC_URL \
  --account $KEYSTORE_NAME \
  --broadcast
```

<Aside type="caution" title="Wait for in-flight transfers to settle before draining">
  - After pausing, wait until all in-flight transfers in **both** directions show a final status in the [CCIP
  Explorer](https://ccip.chain.link/) before you drain liquidity in Step 5. - If you drain the Sepolia v1 pool while a
  Arbitrum → Sepolia (mint → release) message is still in flight, that message would try to release from the now-empty
  v1 pool: which is still the registered pool until cutover, and fail.
</Aside>

</AnchoredAccordion>

<AnchoredAccordion
  title="Step 5: Migrate locked liquidity into the LockBox (Ethereum Sepolia only)"
  number={5}
  depth={3}
>

This step is unique to Lock & Mint. In v1 the Lock & Release pool held liquidity directly in its own balance; in v2 that liquidity lives in the `ERC20LockBox`. You must move it.

<Aside type="caution" title="Non-atomic custody">
  Executed as separate EOA transactions, the drained tokens sit in **your wallet** between the withdrawal and the
  deposit. Use a secure signer (for example, a hardware wallet). Teams that require atomicity can batch these calls
  through a Safe multisig meta-transaction, which is outside the scope of this guide.
</Aside>

First, export the address of your keystore account (it must be the v1 pool owner and will be the temporary rebalancer and lockbox depositor):

```bash filename="Terminal"
export MY_ADDRESS=0xYourKeystoreAccountAddress
```

<GitHubCard
  title="GetRebalancer.s.sol"
  href="https://github.com/smartcontractkit/docs-cct-foundry/blob/main/script/configure/liquidity/GetRebalancer.s.sol"
  iconName="github-svg-card"
>
  View the rebalancer query script on GitHub.
</GitHubCard>

1. (Optional) Read the current rebalancer on the v1 pool:

```bash filename="Terminal"
TOKEN_POOL=$ETHEREUM_SEPOLIA_V1_POOL forge script \
  script/configure/liquidity/GetRebalancer.s.sol \
  --rpc-url $ETHEREUM_SEPOLIA_RPC_URL
```

<GitHubCard
  title="SetRebalancer.s.sol"
  href="https://github.com/smartcontractkit/docs-cct-foundry/blob/main/script/configure/liquidity/SetRebalancer.s.sol"
  iconName="github-svg-card"
>
  View the set-rebalancer script on GitHub.
</GitHubCard>

2. Set yourself as the rebalancer on the v1 pool (only the rebalancer can withdraw liquidity; this call must be sent by the **pool owner**):

```bash filename="Terminal"
TOKEN_POOL=$ETHEREUM_SEPOLIA_V1_POOL \
  REBALANCER=$MY_ADDRESS \
  forge script \
  script/configure/liquidity/SetRebalancer.s.sol \
  --rpc-url $ETHEREUM_SEPOLIA_RPC_URL \
  --account $KEYSTORE_NAME \
  --broadcast
```

  title="WithdrawLiquidity.s.sol"

<Aside type="caution" title="Rollback is harder for Lock & Mint">
  You can roll back by calling <code>setPool</code> again and pointing back to your v1 pool on a chain. But for Lock &
  Mint this is painful once you have cut over: the Sepolia v1 pool has been drained, so you would first have to re-fund
  it (via <code>provideLiquidity</code> as its rebalancer) before it can release again, and liquidity is now split
  between the old pool and the lockbox. Prefer resolving issues <strong>before</strong> the liquidity migration in Step
  5.
</Aside>
