In this tutorial you will:

1. Deploy a token on two chains using [Hardhat](https://hardhat.org/).
2. Set up a `Burn Mint` token pool on each chain.
3. Configure and activate the pools in CCIP so your token becomes a Cross-Chain Token (CCT).
4. (Optional) Test the setup by minting and transferring tokens across networks.

<Aside type="note" title="If you do not explicitly configure these features, default behavior applies">
  <ol>
    <li>
      <strong>Default finality:</strong> Transfers use the chain's native finality (equivalent to omitting{" "}
      <code>finality</code> or using <code>finality=finalized</code>) unless you opt into faster than finality via{" "}
      <code>finality</code> (for example, <code>finality=&lt;N&gt;</code> for block-depth faster than finality).
    </li>
    <li>
      <strong>Opt-in changes.</strong> New v2 behavior only applies when you explicitly configure it (for example,
      pool-level fees or faster than finality).
    </li>
  </ol>
</Aside>

## Before You Begin

<AnchoredAccordion title="Set up your development environment" number={1} depth={3}>

1. Install Node.js and npm:
   - Make sure you have `Node.js v22.10.0` or above installed. If not, install **`Node.js v22.10.0`** using their [documentation](https://nodejs.org/en/download/).
   - `npm` is bundled with Node.js. If you can’t run `npm`, reinstall/update Node.js from the official installer.

2. Install/Update [Chainlink CCIP-CLI](https://docs.chain.link/ccip/tools/cli/), you can also find the [GitHub repository here](https://github.com/smartcontractkit/ccip-cli).

```bash filename="Terminal"
npm install -g @chainlink/ccip-cli
```

Verify the installation by running the following command:

```bash filename="Terminal"
ccip-cli --version
```

3. **Clone the repository and navigate to the project directory**:

```bash filename="Terminal"
git clone https://github.com/smartcontractkit/docs-cct-hardhat.git

```

4. Create a `.env` file by copying the `.env.example` file, and fill in the required values:


```bash filename=".env"
KEYSTORE_NAME=<your_private_key_name>

# RPC URLs (add the ones you need)
```

<AnchoredAccordion title="How to configure deployment parameters?" number={2} depth={3}>

Deployment parameters can be configured in two ways:

1. Edit the `.json` files in `input/`.
2. Pass CLI flags inline at runtime.

> **Note:** CLI flags take precedence over `.json` file values.

#### Token Deployment Configuration

Default values live in `input/token.json`:

```json filename="input/token.json"
{
  "name": "BnM Test",
  "symbol": "BnM-T",
  "decimals": 18,
  "maxSupply": 0,
  "preMint": 0,
  "tokenAmountToMint": 1000000000000000000000,
  "tokenAmountToTransfer": 1000000000000000000
}
```

Deployment fields can be overridden with CLI flags:

| Flag          | Overrides (`token.json`) | Description                                   |
| ------------- | ------------------------ | --------------------------------------------- |
| `--name`      | `.name`                  | Token name                                    |
| `--symbol`    | `.symbol`                | Token symbol                                  |
| `--decimals`  | `.decimals`              | Decimal places (usually `18`)                 |
| `--maxsupply` | `.maxSupply`             | Max supply in smallest unit (`0` = unlimited) |
| `--premint`   | `.preMint`               | Amount pre-minted to deployer (`0` = none)    |

#### (Optional) Advanced Pool Hooks

<CcipCommon callout="advancedPoolHooks" />

Default values live in `input/advanced-pool-hooks.json`:

```json filename="input/advanced-pool-hooks.json"
{
  "allowlist": [],
  "thresholdAmount": 0,
  "policyEngine": "0x0000000000000000000000000000000000000000",
  "authorizedCallers": []
}
```

All fields can be overridden with CLI flags:

| Flag                  | Overrides (`advanced-pool-hooks.json`) | Description                                                                              |
| --------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| `--allowlist`         | `.allowlist`                           | Addresses allowed to transfer (comma-separated)                                          |
| `--thresholdamount`   | `.thresholdAmount`                     | Threshold amount after which additional hook checks/policy checks may apply (`0` = none) |
| `--policyengine`      | `.policyEngine`                        | Policy engine contract address                                                           |
| `--authorizedcallers` | `.authorizedCallers`                   | Addresses authorized to call the hooks (comma-separated)                                 |

> **Note:** To configure an `AdvancedPoolHooks` sender allowlist, follow [Configure a sender allowlist with AdvancedPoolHooks using Hardhat](/ccip/evm/tutorials/cross-chain-tokens/configure-sender-allowlist-advanced-pool-hooks-hardhat). For an overview of the other hook capabilities, read [Advanced Pool Hooks](/ccip/concepts/cross-chain-token/advanced-pool-hooks).

**Already have deployments? Skip only what you already have:**

- If you already have tokens deployed on **both** chains, skip **Deploy Tokens**.
- If you have deployed tokens but not the corresponding pools, you must still run **Deploy Token Pools** before continuing.
- If you already have tokens and **V2-compatible** token pools deployed on **both** chains, skip both sections and move straight on to [Enablement](#enablement).

**If you already have a V1 token pool deployed and want to use newer features or prepare for lane migration:**

- You will need to deploy a **V2-compatible token pool**
- Your existing V1 pool can continue to support current transfers
- Follow the migration guide to upgrade your setup without disrupting your existing deployment

> **Read**: [Migrate from V1 to V2 token pools](/ccip/evm/tutorials/cross-chain-tokens/migrate-from-v1-to-v2-burn-mint-hardhat)

### Enablement

These steps configure your token pools and activate them under the CCIP protocol so your token becomes a truly Cross-Chain Token (CCT).

<AnchoredAccordion title="Claim Admin Role" number={1} depth={4}>

Use the `claimAdmin` task to register your EOA as the administrator for the deployed tokens on both chains. \
This process involves interacting with the [`RegistryModuleOwnerCustom`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/tokenAdminRegistry/RegistryModuleOwnerCustom.sol) contract to set up your EOA as the admin.

<Aside type="note" title="Supported admin patterns">
  The task auto-detects how your token exposes its admin and uses the appropriate registration method:
  <ol>
    <li>
      If your token implements <code>getCCIPAdmin()</code>, the task calls <code>registerAdminViaGetCCIPAdmin()</code>.
    </li>
    <li>
      If your token uses OpenZeppelin's <code>Ownable</code> pattern (<code>owner()</code>), the task calls{" "}
      <code>registerAdminViaOwner()</code> instead.
    </li>
  </ol>
  No extra configuration is needed: both patterns are fully supported.
</Aside>

<AnchoredAccordion title="Configure Token Pools" number={3} depth={4}>

Use the `applyChainUpdates` task to initialize the token pool configuration on each blockchain to enable cross-chain transfers between the two chains. \
This involves linking the token pool on one blockchain to its corresponding pool on the other blockchain, allowing cross-chain token transfers.\
You will interact with the [`TokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/TokenPool.sol) contract by calling the `applyChainUpdates()` function to set up cross-chain parameters and rate limits.

`applyChainUpdates()` registers the destination chain and the destination pool on the local pool by recording:

- The remote chain selector (to identify the exact chain),
- The remote pool address (to identify the exact pool on that exact chain),
- The remote token address (to identify the exact token on the remote pool),
- And per-direction rate limit buckets (outbound and inbound).

You must run it on **both** pools so each side knows its counterpart.

  title="applyChainUpdates.ts"

</GitHubCard>

<Aside type="caution" title="Rate Limiting">
  <ol>
    <li>
      Rate limiting is disabled by default (`isEnabled: false`). With rate limiting disabled, there are **no
      restrictions** on the volume of tokens that can be transferred through the pool in any direction.
    </li>
    <li>
      To protect against large, unexpected outflows, set `isEnabled` to `true` and configure `capacity` (maximum bucket
      size) and `rate` (tokens refilled per second).
    </li>
    <li>
      See the [Update Rate Limiters](/ccip/evm/tutorials/cross-chain-tokens/update-rate-limiters-hardhat) tutorial for
      more details.
    </li>
  </ol>
</Aside>

| --------------------------------- | -------- | ------------------------------------------------------------------- |
| <nobr>`--destchain`</nobr>        | Yes      | Destination chain name (e.g. `arbitrumSepolia`, `ARBITRUM_SEPOLIA`) |

<AnchoredAccordion title="(Optional) Configure Faster Than Finality for the Token Pool" number={4} depth={4}>

1. CCIP 2.0 supports **faster than finality** as an opt-in feature, letting token issuers control the speed vs. security
   tradeoff for cross-chain transfers of their token.

2. By default, a newly deployed token pool only allows transfers at default finality (equivalent to omitting `finality`
   or using `finality=finalized`).

3. To enable faster than finality, the pool owner must configure which faster than finality modes are allowed. Senders then request
   one mode per transfer using `finality` (either `finality=finalized` or `finality=<N>` for block-depth faster than finality).

> This section applies only to [**token pools with versions ≥ 2.0**](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/TokenPool.sol). Existing v1 pools do not support fast
> finality.

<Aside type="note" title="Pool-level finality vs. transaction-level finality">
  <ol>
    <li>
      <strong>Pool-level finality</strong> (allowed finality config): A setting the pool owner configures via{" "}
      <code>setAllowedFinalityConfig(bytes4)</code>.
      <ul>
        <li>
          Default = faster than finality is <strong>disabled</strong>. The pool only allows transfers that use default
          finality (omit <code>finality</code> or use <code>finality=finalized</code>).
        </li>
        <li>
          The pool can opt in to faster than finality by allowing a minimum block depth (<code>finality=&lt;N&gt;</code>
          ).
        </li>
      </ul>
    </li>
    <li>
      <strong>Transaction-level finality</strong> (<code>finality</code>): A per-transfer setting the sender specifies
      via extra args when sending a CCIP message.
      <ul>
        <li>
          <code>finality=finalized</code> (or omit <code>finality</code>) = default finality. This is always allowed.
        </li>
        <li>
          <code>finality=&lt;N&gt;</code> = faster than finality using block depth (block confirmations). Only succeeds
          if the pool allows block-depth mode and the requested <code>N</code> is &ge; the pool's configured minimum.
        </li>
      </ul>
      Each transfer requests exactly <strong>one</strong> finality mode.
    </li>
  </ol>
  Faster Than Finality transfers use the <strong>faster than finality</strong> rate limit bucket when configured. If the
  faster than finality bucket isn’t configured for a lane, the pool falls back to the standard rate limit bucket.
</Aside>

<AnchoredAccordion title="Transfer Tokens Across Networks" number={2} depth={4}>

Use the `ccip-cli` command to securely transfer tokens across networks from your terminal.
Tokens will be:

1. **burned** on the source chain (Ethereum Sepolia), and,
2. **minted** on the destination chain (Arbitrum Sepolia). \

You can choose to pay CCIP fees using LINK tokens or the native gas token.

> **Note:**
>
> 1. Add `--fee-token LINK` to pay CCIP fees in LINK. If you omit this flag, fees are paid in the native gas token.
> 2. Use `--receiver <address>` for a custom recipient. If omitted on EVM-to-EVM, the receiver defaults to the sender.

The CLI command expects the router address to be set in the environment variables. You can set it using the following command:

```bash filename="Terminal"
export ETHEREUM_SEPOLIA_ROUTER=0x...
```

<Aside type="note" title="Router address">
  You can find the router address for your chain in the [CCIP
  Directory](https://docs.chain.link/ccip/directory/testnet).
</Aside>

1. Transfer tokens from Ethereum Sepolia to Arbitrum Sepolia on **default finality**:

```bash filename="Terminal"
ccip-cli send \
  --source ethereum-testnet-sepolia \
  --router $ETHEREUM_SEPOLIA_ROUTER \
  --dest ethereum-testnet-sepolia-arbitrum-1 \
  --transfer-tokens $ETHEREUM_SEPOLIA_TOKEN=1.23 \
  --receiver 0xYourReceiverAddress \
  --wallet hardhat:$KEYSTORE_NAME \
  --rpc "$ETHEREUM_SEPOLIA_RPC_URL" \
  --rpc "$ARBITRUM_SEPOLIA_RPC_URL"
```

Your output should look something like this:

```

✔ Enter password for Hardhat keystore 'PRIVATE_KEY'
🚀 Sending message to 0xE23Fc63F47F08F58B9d7448d4CCE0bCDcc96d7F3 @ ethereum-testnet-sepolia-arbitrum-1 , tx => 0x3dc40bea29f3e3fc93ff8fce0dda45fd7f55a07ace5089646e018874c8b6745e , messageId => 0x4a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293
```

<Aside type="note" title="chainId vs. chainSelector">
  The <code>chainId</code> column shows the EVM chain ID (for example, <code>11155111</code> for Sepolia). The{" "}
  <code>chainSelector</code> is CCIP's own chain identifier used internally by the protocol. You do not need to set
  chain selectors yourself; the CLI and tasks resolve them automatically from the chain name.
</Aside>

2. Transfer tokens from Ethereum Sepolia to Arbitrum Sepolia using **faster than finality**:

This assumes you enabled faster than finality on the pool in the optional finality configuration accordion above.
When you pass <code>--extra finality=...</code>, <code>ccip-cli</code> encodes it into the CCIP message extra args.

Transfer with explicit finalized finality (`finality=finalized`):

```bash filename="Terminal"
ccip-cli send \
  --source ethereum-testnet-sepolia \
  --router $ETHEREUM_SEPOLIA_ROUTER \
  --dest ethereum-testnet-sepolia-arbitrum-1 \
  --transfer-tokens $ETHEREUM_SEPOLIA_TOKEN=1.23 \
  --receiver 0xYourReceiverAddress \
  --extra finality=finalized \
  --wallet hardhat:$KEYSTORE_NAME \
  --rpc "$ETHEREUM_SEPOLIA_RPC_URL" \
  --rpc "$ARBITRUM_SEPOLIA_RPC_URL"
```

Your output should look something like this:


```bash filename="Terminal"
ccip-cli send \
  --source ethereum-testnet-sepolia \
  --router $ETHEREUM_SEPOLIA_ROUTER \
  --dest ethereum-testnet-sepolia-arbitrum-1 \
  --transfer-tokens $ETHEREUM_SEPOLIA_TOKEN=1.23 \
  --receiver 0xYourReceiverAddress \
  --extra finality=7 \
  --wallet hardhat:$KEYSTORE_NAME \
```

<Aside type="note" title="Understand Minimum Block Depth Requirements 🧑‍🏫">
  <ol>
    <li>
      The last command failed because the pool's <strong>allowed finality config</strong> requires a larger block depth
      for numeric faster than finality (for example, if you configured <code>--blockdepth 32</code>) but we requested{" "}
      <code>finality=7</code>.
    </li>
    <li>
      Try running the command again with an appropriate value for <code>finality</code> (for example,{" "}
      <code>--extra finality=20</code>), or omit <code>finality</code> to use default finality (
      <code>finality=finalized</code>).
    </li>
    <li>
      If you see a revert like <code>InvalidRequestedFinality(requestedFinality, allowedFinality)</code>, it means the
      requested mode (or depth) is not permitted by the pool.
    </li>
  </ol>
</Aside>
