In this tutorial you will:

1. Deploy a token on two chains using [Foundry](https://book.getfoundry.sh/).
2. Set up a `Lock & Release` token pool on the source chain and a `Burn Mint` token pool on the destination chain.
3. Configure and activate the pools in CCIP so your token becomes a Cross-Chain Token (CCT).
4. (Optional) Test the setup by minting and transferring tokens across networks.

<Aside type="note" title="If you do not explicitly configure these features, default behavior applies">
  <ol>
    <li>
      <strong>Default finality:</strong> Transfers use the chain's native finality (equivalent to omitting{" "}
      <code>finality</code> or using <code>finality=finalized</code>) unless you opt into faster than finality via{" "}
      <code>finality</code> (for example, <code>finality=32</code>).
    </li>
    <li>
      <strong>Opt-in changes.</strong> New v2 behavior only applies when you explicitly configure it (for example,
      pool-level fees or faster than finality).
    </li>
  </ol>
</Aside>

## Before You Begin

<AnchoredAccordion title="Set up your development environment" number={1} depth={3}>

1. Install Node.js and npm:
   - Make sure you have `Node.js v22.10.0` or above installed. If not, install **`Node.js v22.10.0`** using their [documentation](https://nodejs.org/en/download/).

2. Install/Update [Chainlink CCIP-CLI](https://docs.chain.link/ccip/tools/cli/). You can also find the [GitHub repository here](https://github.com/smartcontractkit/ccip-cli).

```bash filename="Terminal"
npm install -g @chainlink/ccip-cli
```

Verify the installation by running the following command:

```bash filename="Terminal"
ccip-cli --version
```

3. **Install Foundry**:
   If you haven't already, follow the instructions in the [Foundry documentation](https://book.getfoundry.sh/getting-started/installation) to install Foundry. \
   Verify the installation by running the following command:

```bash filename="Terminal"
forge --version
```

4. **Clone the repository and navigate to the project directory**:

<GitHubCard

```bash filename="Terminal"
git clone https://github.com/smartcontractkit/docs-cct-foundry.git
cd docs-cct-foundry
```

5. Create an encrypted Foundry keystore, if you haven't already:

```bash filename="Terminal"
cast wallet import your_keystore_name --interactive
```

<AnchoredAccordion title="How to configure deployment parameters?" number={2} depth={3}>

Deployment parameters can be configured in two ways:

1. Edit the `.json` files in `script/input/`.
2. Pass environment variables inline at runtime.

> **Note:** Environment variables take precedence over `.json` file values.

#### Token Deployment Configuration

Default values live in `script/input/token.json`:

```json filename="script/input/token.json"
{
  "name": "BnM Test",
  "symbol": "BnM-T",
  "decimals": 18,
  "maxSupply": 0,
  "preMint": 0,
  "tokenAmountToMint": 1000000000000000000000,
  "tokenAmountToTransfer": 1000000000000000000
}
```

Deployment fields can be overridden with inline env vars:

| Env var                                 | Overrides (`token.json`) | Optional | Description                                                                                                  |
| --------------------------------------- | ------------------------ | -------- | ------------------------------------------------------------------------------------------------------------ |
| <nobr>`TOKEN_NAME`</nobr>               | `.name`                  | Yes      | Token name                                                                                                   |
| <nobr>`TOKEN_SYMBOL`</nobr>             | `.symbol`                | Yes      | Token symbol                                                                                                 |
| <nobr>`TOKEN_DECIMALS`</nobr>           | `.decimals`              | Yes      | Decimal places (usually `18`)                                                                                |
| <nobr>`TOKEN_MAX_SUPPLY`</nobr>         | `.maxSupply`             | Yes      | Max supply in smallest unit (`0` = unlimited)                                                                |
| <nobr>`TOKEN_PRE_MINT`</nobr>           | `.preMint`               | Yes      | Amount pre-minted to the configured recipient (`0` = none)                                                   |
| <nobr>`TOKEN_PRE_MINT_RECIPIENT`</nobr> | N/A (env-only)           | Yes      | Address receiving pre-minted tokens. If omitted and `TOKEN_PRE_MINT > 0`, the script defaults to broadcaster |
| <nobr>`CCIP_ADMIN_ADDRESS`</nobr>       | N/A (env-only)           | Yes      | Address assigned as CCIP admin on the token. If omitted, broadcaster is used                                 |

#### (Optional) Advanced Pool Hooks

<CcipCommon callout="advancedPoolHooks" />

Default values live in `script/input/advanced-pool-hooks.json`:

```json filename="script/input/advanced-pool-hooks.json"
{
  "allowlist": [],
  "thresholdAmount": 0,
  "policyEngine": "0x0000000000000000000000000000000000000000",
  "authorizedCallers": []
}
```

All fields can be overridden with inline env vars:

| Env var                           | Overrides (`advanced-pool-hooks.json`) | Optional | Description                                                                              |
| --------------------------------- | -------------------------------------- | -------- | ---------------------------------------------------------------------------------------- |
| <nobr>`ALLOWLIST`</nobr>          | `.allowlist`                           | Yes      | Addresses allowed to transfer (CSV or JSON array)                                        |
| <nobr>`THRESHOLD_AMOUNT`</nobr>   | `.thresholdAmount`                     | Yes      | Threshold amount after which additional hook checks/policy checks may apply (`0` = none) |
| <nobr>`POLICY_ENGINE`</nobr>      | `.policyEngine`                        | Yes      | Policy engine contract address                                                           |
| <nobr>`AUTHORIZED_CALLERS`</nobr> | `.authorizedCallers`                   | Yes      | Addresses authorized to call the hooks (CSV or JSON array)                               |

> **Note:** To configure an `AdvancedPoolHooks` sender allowlist, follow [Configure a sender allowlist with AdvancedPoolHooks using Foundry](/ccip/evm/tutorials/cross-chain-tokens/configure-sender-allowlist-advanced-pool-hooks-foundry). For an overview of the other hook capabilities, read [Advanced Pool Hooks](/ccip/concepts/cross-chain-token/advanced-pool-hooks).

</AnchoredAccordion>

**Already have deployments? Skip only what you already have:**

- If you already have tokens deployed on **both** chains, skip **Deploy Tokens**.
- If you have deployed tokens but not the corresponding pools and lockbox, you must still run **Deploy Token Pools** before continuing.
- If you already have tokens deployed on **both** chains, **V2-compatible** token pools deployed on **both** chains, and the lockbox deployed on the **Lock & Release** side (Ethereum Sepolia), skip both sections and move straight on to [Enablement](#enablement).

**If you already have a V1 token pool deployed and want to use newer features or prepare for lane migration:**

- You will need to deploy a **V2-compatible token pool**
- Your existing V1 pool can continue to support current transfers
- Follow the migration guide to upgrade your setup without disrupting your existing deployment

> **Read**: [Migrate from V1 to V2 token pools](/ccip/evm/tutorials/cross-chain-tokens/migrate-from-v1-to-v2-lock-mint-foundry)

<AnchoredAccordion title="Deploy Tokens" number={1} depth={4}>

<Aside type="tip" title="Already have tokens deployed?">
  <ul>
    <li>
      Your source chain token (canonical token) does **NOT** need to support burn and mint (this tutorial deploys a Lock
      & Release pool on the source chain). Your destination chain token **MUST** support burn and mint operations (this
      tutorial deploys a Burn & Mint pool on the destination chain).
    </li>
    <li>
      Both tokens must implement either `getCCIPAdmin()` or OpenZeppelin's `owner()` so the `Claim Admin Role` step can
      identify the token administrator.
    </li>
  </ul>
</Aside>

Use the `DeployToken.s.sol` script to deploy your tokens on two testnets, Ethereum Sepolia and Arbitrum Sepolia. The destination chain token (Arbitrum Sepolia) implements the [`IBurnMintERC20`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/interfaces/IBurnMintERC20.sol) interface, which exposes the `mint` and `burn` functions that the Burn & Mint token pool later calls during cross-chain transfers. The source chain token (Ethereum Sepolia) does not need burn/mint support; it is locked in the lockbox by the Lock & Release pool.

> **Note:** The script reads the `script/input/token.json` file to get the token name, symbol, decimals, maximum supply, and pre-mint amount. \
> You can also override these values by providing inline environment variables at runtime. \
> See [how to configure deployment parameters](/ccip/evm/tutorials/cross-chain-tokens/register-from-eoa-lock-mint-foundry#token-deployment-configuration) for more details.

<AnchoredAccordion title="Configure Token Pools" number={3} depth={4}>

Use the `ApplyChainUpdates.s.sol` script to link each token pool to its counterpart on the other chain and configure rate limits. \
You will interact with the [`TokenPool`](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/TokenPool.sol) contract by calling the `applyChainUpdates()` function to enable cross-chain transfers.

`applyChainUpdates()` registers the destination chain and the destination pool on the local pool by recording:

- The remote chain selector (to identify the exact chain),
- The remote pool address (to identify the exact pool on that exact chain),
- The remote token address (to identify the exact token on the remote pool),
- And per-direction rate limit buckets (outbound and inbound).

You must run it on **both** pools so each side knows its counterpart.

>
  View the pool configuration script on GitHub.
</GitHubCard>

<Aside type="caution" title="Rate Limiting">
  <ol>
    <li>
      Rate limiting is disabled by default (`isEnabled: false`). With rate limiting disabled, there are **no
      restrictions** on the volume of tokens that can be transferred through the pool in any direction.
    </li>
    <li>

      size) and `rate` (tokens refilled per second).
    </li>

      more details.
    </li>
  </ol>

<AnchoredAccordion
  title="(Optional) Configure Faster Than Finality for the Token Pool"
  number={4}
  depth={4}
  anchorId="optional-configure-fast-finality-for-the-token-pool"
>

1. CCIP 2.0 supports **faster than finality** as an opt-in feature, letting token issuers control the speed vs. security
   tradeoff for cross-chain transfers of their token.

2. By default, a newly deployed token pool only allows transfers at default finality (equivalent to omitting `finality`
   or using `finality=finalized`).

3. To enable faster than finality, the pool owner must configure which faster than finality modes are allowed. Senders then request
   faster than finality per transfer using a numeric block depth via `finality=<N>` (minimum recommended depth: `32`).

> This section applies only to [**token pools with versions ≥ 2.0**](https://github.com/smartcontractkit/chainlink-ccip/tree/contracts-ccip-v2.0.0/chains/evm/contracts/pools/TokenPool.sol). Existing v1 pools do not support fast
> finality.
>
> In this tutorial, configure faster than finality on both token pools: the `Lock & Release` pool on Ethereum Sepolia and the
> `Burn Mint` pool on Arbitrum Sepolia.

<Aside type="note" title="Pool-level finality vs. transaction-level finality">
  <ol>
    <li>
      <strong>Pool-level finality</strong> (allowed finality config): A setting the pool owner configures via{" "}
      <code>setAllowedFinalityConfig(bytes4)</code>.
      <ul>
        <li>
          Default = faster than finality is <strong>disabled</strong>. The pool only allows transfers that use default
          finality (omit <code>finality</code> or use <code>finality=finalized</code>).
        </li>
        <li>
          The pool can opt in to faster than finality by allowing a minimum block depth (<code>finality=&lt;N&gt;</code>
          ).
        </li>
      </ul>
    </li>
    <li>
      <strong>Transaction-level finality</strong> (<code>finality</code>): A per-transfer setting the sender specifies
      via extra args when sending a CCIP message.
      <ul>
        <li>
          <code>finality=finalized</code> (or omit <code>finality</code>) = default finality. This is always allowed.
        </li>
        <li>
          <code>finality=&lt;N&gt;</code> = faster than finality using block depth (block confirmations). Only succeeds
          if the pool allows block-depth mode and the requested <code>N</code> is &ge; the pool's configured minimum.
        </li>
      </ul>
      Each transfer uses either default finality or block depth.
    </li>
  </ol>
  Faster Than Finality transfers use the <strong>faster than finality</strong> rate limit bucket when configured. If the
  faster than finality bucket isn’t configured for a lane, the pool falls back to the standard rate limit bucket.
</Aside>

<AnchoredAccordion title="Transfer Tokens Across Networks" number={2} depth={4}>

Use the `ccip-cli` command to securely transfer tokens across networks from your terminal.
Tokens will be:

1. **locked** on the source chain (Ethereum Sepolia), and,
2. **minted** on the destination chain (Arbitrum Sepolia). \

You can choose to pay CCIP fees using LINK tokens or the native gas token.

> **Note:**
>
> 1. Add `--fee-token LINK` to pay CCIP fees in LINK. If you omit this flag, fees are paid in the native gas token.
> 2. Use `--receiver <address>` for a custom recipient. If omitted on EVM-to-EVM, the receiver defaults to the sender.

The CLI command expects the router address to be set in the environment variables. You can set it using the following command:

```bash filename="Terminal"
export ETHEREUM_SEPOLIA_ROUTER=0x...
```

<Aside type="note" title="Router address">
  You can find the router address for your chain in the [CCIP
  Directory](https://docs.chain.link/ccip/directory/testnet).
</Aside>

<Aside type="note" title="Token amounts in this tutorial">
  Earlier Foundry scripts use smallest-unit amounts (wei-like). In the <code>ccip-cli</code> examples below we use a
  compact, human-readable token amount (for example, <code>1.23</code>).
</Aside>

1. Transfer tokens from Ethereum Sepolia to Arbitrum Sepolia on **default finality**:

```bash filename="Terminal"
ccip-cli send \
  --source ethereum-testnet-sepolia \
  --router $ETHEREUM_SEPOLIA_ROUTER \
  --dest ethereum-testnet-sepolia-arbitrum-1 \
  --transfer-tokens $ETHEREUM_SEPOLIA_TOKEN=1.23 \
  --receiver 0xYourReceiverAddress \
  --wallet foundry:$KEYSTORE_NAME \
  --rpc "$ETHEREUM_SEPOLIA_RPC_URL" \
  --rpc "$ETHEREUM_TESTNET_SEPOLIA_ARBITRUM_1_RPC_URL"
```

  <ol>
    <li>
      If a transfer reverts with <code>InvalidRequestedFinality(requestedFinality, allowedFinality)</code>, it usually
      means the pool requires a larger block depth than you requested (for example, the pool minimum is <code>32</code>{" "}
      but you requested a smaller value).
    </li>

    </li>
    <li>Other reverts may indicate the requested depth (or mode) is not permitted by the pool.</li>
  </ol>
