## Authentication

All connections to the Data Streams WebSocket API require authentication. For comprehensive documentation on generating authentication headers and implementing the HMAC authentication process, please refer to the [Data Streams Authentication](/data-streams/reference/data-streams-api/authentication) page.

**Note**: If you're using a [Data Streams SDK](/data-streams/reference/data-streams-api/go-sdk), you don't need to manually generate authentication headers.

### Headers

All routes require the following three headers for user authentication:

| Header                             | Description                                                                                                                                                                      |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Authorization`                    | The user's unique identifier, provided as a UUID (Universally Unique IDentifier).                                                                                                |
| `X-Authorization-Timestamp`        | The current timestamp, with precision up to milliseconds. The timestamp must closely synchronize with the server time, allowing a maximum discrepancy of 5 seconds (by default). |
| `X-Authorization-Signature-SHA256` | The HMAC (Hash-based Message Authentication Code) signature, generated by hashing parts of the request and its metadata using SHA-256 with a shared secret key.                  |

## WebSocket Connection

Establish a streaming WebSocket connection that sends reports for the given stream ID(s) after they are verified.

##### Endpoint

**`/api/v1/ws`**

| Type      | Parameter(s)                                                  |
| --------- | ------------------------------------------------------------- |
| WebSocket | `feedIDs`: A comma-separated list of Data Streams stream IDs. |

##### Sample request

```http
GET /api/v1/ws?feedIDs=<feedID1>,<feedID2>,...
```

##### Sample response

```json
{
  "report": {
    "feedID": "hex encoded feedId",
    "fullReport": "a blob containing the report context + body, can be passed unmodified to the contract for verification"
  }
}
```

## Connection closures and reconnecting

WebSocket connections to Data Streams are not guaranteed to stay open indefinitely. The server closes connections during routine operations such as deployments, server rotation, and failover. This is expected behavior, and your client should be built to handle it.

Data Streams sends close code **`1000`** for all server-initiated closures, usually without a reason string. This includes restarts and failover, where [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455#section-7.4.1) would typically use `1001` ("going away"). Do not interpret a `1000` close from the server as the end of your stream or as a problem with your credentials, request, or client. **Always reconnect.**

### Recommended client behavior

- **Reconnect automatically** whenever the connection closes, including on a `1000` close. Following [RFC 6455 section 7.2.3](https://www.rfc-editor.org/rfc/rfc6455#section-7.2.3), delay the first reconnect attempt by a small random amount (for example, 0–5 seconds) and use exponential backoff for subsequent attempts, so that many clients don't reconnect at the same moment.
- **Regenerate authentication headers on every reconnect.** The `X-Authorization-Timestamp` header must be within 5 seconds of server time, so headers from the original connection can't be reused.
- **Expect a brief gap.** Reports typically resume within a few seconds of reconnecting. If your application can't tolerate a gap, use the [REST API](/data-streams/reference/data-streams-api/interface-api) to fetch the latest report for each stream after reconnecting.
- **Keep redundant connections for critical workloads.** The [Data Streams SDKs](/data-streams/reference/data-streams-api/go-sdk) handle reconnection for you and support a high availability mode that maintains connections to multiple origins and deduplicates reports, so a single closed connection doesn't interrupt your stream.

<Aside type="note" title="Close code 1000 is not an error">
  Treat a server-initiated `1000` close as a normal lifecycle event, not a failure. Log it and reconnect. Only escalate
  if reconnect attempts themselves fail, for example with a `401` or `429` response during the handshake (see [Error
  response codes](#error-response-codes)).
</Aside>

## Error response codes

| Status Code           | Description                                                                                                                                                                                                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400 Bad Request       | This error is triggered when: <ul><li>There is any missing/malformed query argument.</li><li>Required headers are missing or provided with incorrect values.</li></ul>                                                                                                                |
| 401 Unauthorized User | This error is triggered when: <ul><li>Authentication fails, typically because the HMAC signature provided by the client doesn't match the one expected by the server.</li><li>A user requests access to a stream without the appropriate permission or that does not exist.</li></ul> |
| 429 Too Many Requests | Indicates the request exceeded your account's rate limit. See the [Rate Limits and Fair Use Policy](/data-streams/rate-limits) page for applicable limits and how to request higher limits.                                                                                           |
| 500 Internal Server   | Indicates an unexpected condition encountered by the server, preventing it from fulfilling the request. This error typically points to issues on the server side.                                                                                                                     |
